# 홈페이지 로딩 속도 개선 전략 (GitHub Pages 정적 호스팅 전제)

작성일: 2026-09-26
대상: `www.tabspace.kr` 홈페이지(`index.html`). **GitHub Pages 정적 호스팅**(Fastly CDN 서울 POP 경유), 저장소 `tabspacekr/tabspacekr.github.io`
목적: "접속하면 너무 느리다"는 평가의 원인을 측정으로 특정하고, 방문자가 체감하는 속도(첫 화면이 보이는 시점, 스크롤·탭 반응, 화면 흔들림)를 우선순위대로 개선한다.
제약: **응답 헤더와 서버를 제어할 수 없다.** 캐시는 `max-age=600`으로 고정되어 있고 압축은 gzip만 된다. 현재 빌드 단계는 기본 Jekyll뿐이다. 사이버 테마의 시각 정체성은 유지하는 것을 기본으로 하고, 모양이 바뀌는 항목은 권고안과 함께 §6-1에 모았다.

> **표기 규칙**: **(측정)**은 도구로 실제로 잰 값이고, **(추정)**은 측정값에서 계산하거나 가정을 더한 값이다. 행 번호는 작성일의 저장소 상태 기준이다. 랩 측정은 대부분 "모바일 412px, 지연 150ms, 1.6Mbps, CPU 4배 감속" 조건으로 했다. 한국 LTE보다 느린 비관적 조건이므로 절대값보다 **변경 전후의 차이**를 근거로 삼는다. 시간은 표 안에서는 s·ms로, 본문에서는 초로 적는다.

> **용어** (이 문서에서 한 번만 설명한다)
> - **히어로**: 첫 화면 상단의 큰 제목·소개문·버튼·그림 영역.
> - **FCP**: 화면에 무엇이든 처음 그려지는 시점. **LCP**: 화면에서 가장 큰 글이나 그림이 그려지는 시점(체감 로딩 완료. 2.5초 이하 '좋음', 4초 초과 '나쁨').
> - **CLS**: 로딩 중 화면이 밀리고 흔들리는 정도(0.1 이하 '좋음', 0.25 초과 '나쁨'). **INP**: 탭·클릭 뒤 화면이 반응하기까지 걸리는 시간(200ms 이하 '좋음', 500ms 초과 '나쁨'). Google은 LCP·INP·CLS 세 지표를 Core Web Vitals라 부른다.
> - **TBT**: 로딩 중 브라우저가 다른 일에 묶여 입력에 반응하지 못한 시간의 합. **롱태스크**: 50ms 넘게 브라우저를 붙잡는 작업. **DOMContentLoaded(DCL)**: HTML과 필수 스크립트 처리가 끝난 시점. 이 홈페이지는 차트·프로젝트·블로그·아이콘을 이 시점 이후에 그린다.
> - **렌더 차단**: 다 받기 전에는 화면을 그릴 수 없는 CSS·스크립트.
> - **랩 측정**: 정해진 속도·기기 조건에서 도구로 잰 값. **RUM(실사용자 측정)**: 실제 방문자 브라우저에서 잰 값. 최종 판정은 RUM으로 한다.
> - **RTT**: 요청이 서버까지 갔다 돌아오는 왕복 시간. **엣지 캐시(POP)**: 방문자 가까운 CDN 서버(서울)가 파일 사본을 보관하는 것. GitHub Pages는 사본을 10분만 보관한다. 그 뒤 첫 방문자는 원본 서버까지 다녀와야 하는데, 이를 '캐시가 식었다'고 쓴다.
> - **FOIT**: 웹폰트를 기다리는 동안 글자가 아예 보이지 않는 현상.
> - **gz / 원본**: gz는 실제로 전송되는 압축 크기, 원본은 압축을 푼 크기(브라우저가 해석하는 양).
> - **프레임 예산 16.7ms**: 화면을 초당 60번 부드럽게 그리려면 한 번의 작업이 16.7ms 안에 끝나야 한다.

## 요약

**왜 느린가.** 서버가 느린 것이 아니다. 호스팅(GitHub Pages)은 이미 서울에서 응답한다. 원인은 홈페이지 코드 안에 있다.

1. 첫 화면 제목·소개문("AI 시대의 IoT")을 외부 스크립트가 모두 실행될 때까지 **일부러 투명하게 숨긴다.** 느린 모바일 망에서 로고는 3.5초에 보이지만 문구는 **7.7초**에야 보인다(측정). jQuery CDN 하나만 실패해도 문구가 끝까지 보이지 않는다.
2. 첫 화면을 여는 동안 **약 2MB**를 받는다. 그중 절반 이상은 첫 화면에 필요 없는 것이다(추정). 예를 들어 모바일이 쓰지 않는 3D 라이브러리, 페이지 맨 아래 그림(593KB), 화면 밖 차트가 있다.
3. 로딩이 끝나도 장식 애니메이션(파티클, 스캔라인 등)이 **쉬지 않고 돈다.** 그래서 스크롤이 끊기고, 버튼 반응에 0.7~0.8초가 걸리고, 화면이 흔들린다(측정, 중저가 폰을 흉내 낸 CPU 4배 감속 조건).
4. 모바일에서는 캐러셀의 점 37개가 가로로 넘쳐 **페이지 전체가 축소되어 보인다**(측정).
5. 별개로 **`https://tabspace.kr`(www 없는 주소)는 인증서가 없어 아예 열리지 않는다**(측정).

**먼저 할 일.** 실사용자 측정 코드를 붙여 기준선을 모은다(7일 또는 한국 모바일 방문 100건 중 먼저 도달하는 시점까지). 기다리는 동안 연출 결정(§6-1)과 www 없는 주소의 인증서 발급을 끝낸다. 그다음 첫 화면 숨김 속성을 지우고 그림 크기를 지정한다(30분). 이것만으로 모바일 첫 화면 문구가 7.7초에서 3.6초로 당겨진다(측정). 이어서 0단계(개발 1~2일, 배포 4회, 빌드 도구 없음, 추가 비용 0원)를 마치면 약 3초 안팎이 된다(추정, §6). www 없는 주소는 서버(Vultr) 관리자가 인증서만 발급하면 해결된다.

**하지 않을 것.** 호스팅 이전과 Cloudflare 무료 프록시는 지금 하지 않는다. Cloudflare 무료 프록시는 한국 사용자를 LA·도쿄·홍콩 서버로 보내 오히려 느려진다(같은 요금제 대역을 쓰는 다른 사이트로 측정).

**결정이 필요한 것.** 연출과 속도가 부딪히는 7건을 권고안과 함께 §6-1에 정리했다. 그중 4건(히어로 등장 연출, 그림 떠다니는 효과, 데스크톱 3D 배경, 모바일 파티클 수준)은 0단계 작업에 바로 필요하므로 착수 전 30분 회의(0-D)에서 정한다.

## 1. 현황 진단 — 측정 기준선

### 1-1. 진단 요점: 왜 느리게 느껴지는가

1. **첫 화면의 핵심 문구가 일부러 숨겨져 있다.** 이것이 가장 큰 원인이다. 히어로 영역(`index.html:118`, `:158`)의 `data-cue` 속성 때문에 `plugins.css:7433-7435`, `7482-7484`가 `opacity:0`을 건다. 이 숨김은 jQuery(외부 CDN), `plugins.js`, `theme.js`를 모두 받아 실행한 뒤 700ms 애니메이션이 끝나야 풀린다. 모바일 느린 4G에서 첫 픽셀은 3.45초지만 그때 보이는 것은 로고뿐이고, **"AI 시대의 IoT" 문구는 7.67초에야 보인다**(측정). Lighthouse가 LCP로 로고를 잡는 것도 이 때문이라, 랩 지표가 체감보다 낙관적으로 나온다. jQuery CDN(cdnjs) 하나만 실패해도 `plugins.js`·`theme.js`가 멈춰 히어로가 끝까지 보이지 않는다(측정: 외부 HTTPS를 모두 차단한 실행에서 히어로 opacity 0 유지. 메커니즘: `theme.js:806`의 `})(jQuery)`).
2. **첫 화면을 그리기 전에 받아야 할 것이 너무 많다.** 렌더를 막는 CSS가 4개, 123KB gz(원본 937KB)이고 그중 약 95%(`style.css`만 보면 97%)가 이 페이지에서 쓰이지 않는다(coverage 측정). `<head>`의 동기 스크립트 3개(118KB)가 같은 시간대에 대역폭과 파서를 차지한다. `style.css:8`의 Google Fonts `@import`는 CSS를 다 받은 뒤에야 서드파티 두 곳으로 가는 직렬 체인을 만든다. 모바일 CPU 4배 조건에서는 첫 스타일 계산·레이아웃에만 0.4~0.8초가 든다.
3. **모바일이 쓰지도 않는 것을 받는다.** three.js(전송 255KB, 압축을 풀면 1.27MB)를 모바일에서도 받아 해석한다(3D는 `3d-effects.js:26`에서 모바일일 때 꺼지는데 import는 무조건 일어남). 이 때문에 DOMContentLoaded가 **2.8초** 늦어지고, 차트·프로젝트·블로그·아이콘 표시가 모두 뒤로 밀린다(측정). Bootstrap JS는 실행되는 기능이 없고, `chatbot-ui.js`는 초기화가 주석 처리되어 있다. 브라우저가 파싱하는 JS는 약 2.9MB다.
4. **화면 밖 이미지가 첫 화면과 대역폭을 다툰다.** 페이지 맨 아래 그림(593KB)을 첫 로드에 받는다. 프로젝트 캐러셀은 카메라 원본 사진을 쓰기 때문에 느린 망에서는 활성 슬라이드가 **4.5~27초 동안 빈 카드**로 보였다(측정).
5. **페이지가 한 번도 쉬지 않는다.** 히어로 파티클 캔버스(모든 쌍을 선으로 잇고 `shadowBlur` 적용, 화면 밖에서도 계속 돎), 무한 CSS 애니메이션 14개, GSAP ScrollTrigger의 상시 rAF 루프가 겹친다. 모바일 4배 조건에서 로드가 끝난 뒤에도 프레임당 18~22ms를 쓴다. 60fps 예산(16.7ms)을 넘으므로 스크롤이 끊기고, 필터 버튼 탭 반응이 0.7~0.8초 걸린다(측정).
6. **화면이 흔들리고, 모바일에서는 축소되어 보인다.** 스캔라인이 `top` 속성을 애니메이션해 매 프레임 레이아웃 이동이 생긴다(CPU 4배 랩에서 CLS 0.13~0.19로 '개선 필요' 구간. CPU 스로틀이 없으면 모바일 0.04~0.06, 데스크톱 0.07~0.11로 '좋음'~경계 구간. 실기기 필드 값은 RUM으로 확인한다). 모바일 캐러셀은 사진 37장에 점(dot)을 하나씩, 모두 37개(약 888px)를 한 줄에 줄바꿈 없이(`cyber-theme.css:909-915`) 그려 가로로 넘친다. 그 결과 레이아웃 폭이 412px에서 646px로 넓어져 **페이지 전체가 축소 표시**된다(측정, 기존 버그).
7. **호스팅 위치는 주 원인이 아니다.** GitHub Pages는 이미 서울 POP에서 응답한다(RTT 대부분 1~4ms. SKT와 KT 수원 프로브는 약 33ms). 다만 캐시가 10분으로 고정이라, 엣지 캐시가 식으면 요청 단계마다 40~215ms가 더해지고 10분 뒤 재방문하면 동일 출처 41건이 다시 요청된다. 전달 계층의 기여는 약 0.3~0.8초로 추정한다. **호스트 이전보다 바이트·JS 감축이 먼저다.**
8. **www 없는 주소가 열리지 않는다.** `https://tabspace.kr`은 인증서가 없어 TLS 오류가 난다(측정). 명함·메신저 링크로 들어온 방문자에게는 "느리다"를 넘어 "안 열린다"로 체감된다.

## 2. GitHub Pages 제약 조건 — 되는 것과 안 되는 것

### 바꿀 수 없는 것

| 항목 | 현재 값 (측정) | 영향 |
|---|---|---|
| `cache-control` | HTML·CSS·JS·폰트·이미지 모두 `max-age=600` | 10분 뒤 재방문 시 재검증, 엣지 캐시도 10분마다 식음 |
| 압축 | br을 요청해도 gzip만 제공 | brotli 대비 텍스트 약 73KB(-23%) 손해 (추정) |
| HTTP/3, HSTS, 커스텀 헤더 | 없음, 설정 불가 | `immutable` 장기 캐시 불가 |
| ETag | `mtime-size` 형식이라 배포 때마다 모든 파일 값이 바뀜 | 배포 직후 재방문자는 바뀌지 않은 파일까지 다시 받음 (추정) |
| 엣지 캐시 키 | **쿼리스트링을 무시함** (측정: `?a=`, `?b=`가 같은 캐시 적중) | `?v=2`로는 엣지 캐시를 무효화할 수 없음. **파일명을 바꿔야 함** |
| 빌드 | 기본 Jekyll(safe 모드), Node 도구 실행 불가 | PurgeCSS·이미지 변환은 Pages 안에서 불가 |

### 정적 파일 수정만으로 가능한 것

§6의 0~1단계는 **모두 여기에 해당한다.** HTML 속성 수정, `defer`와 동적 `import()`, CSS 수정, 라이브러리·폰트 자체 호스팅(파일 복사), 로컬에서 한 번 변환·생성한 이미지·폰트·CSS 파일 커밋(도구는 개발자 PC에서 실행), IntersectionObserver 기반 지연 실행이 여기에 속한다.

### 빌드 도구가 열어주는 것

PurgeCSS, 이미지 일괄 변환, JS 번들·압축, 콘텐츠 해시 파일명, Lighthouse CI 예산 검사가 가능해진다. 방식은 두 가지다.

| 방식 | 내용 | 장점 | 주의 |
|---|---|---|---|
| **A. 로컬 스크립트 + 산출물 커밋 (기본 권장)** | 개발자 PC에서 도구를 실행해 결과물을 커밋. 2단계부터 CI가 "재생성 결과와 커밋본이 같은지"만 검사 | 배포 방식 그대로, 롤백 쉬움 | 재생성 누락은 CI 검사로 막음 |
| B. Pages 소스를 GitHub Actions로 전환 | `actions/jekyll-build-pages` → `_site` 후처리 → `upload-pages-artifact` → `deploy-pages` | 완전 자동화, 레거시 빌드의 시간당 10회 한도 해제 | 저장소 관리자 설정 필요. **저장소 루트를 그대로 업로드하면 `_config.yml` exclude가 무시되어 `docs/` 등 내부 문서가 공개된다.** 반드시 Jekyll 빌드를 거칠 것 |

방식 A는 1단계에서 CSS 퍼지(C2)와 사진 축소(I4-a)에 바로 쓴다. 도구를 저장소 밖(또는 `npx`)에서 실행하고 산출물만 커밋하면 저장소 설정을 바꿀 필요가 없다. `package.json`·`scripts/`를 저장소에 두는 순간(2단계의 CI 동일성 검사부터)에는 `_config.yml`의 `exclude`에 `node_modules/`, `package.json`, `package-lock.json`, `scripts/`를 추가해야 한다. Jekyll 3.10에서는 사용자가 지정한 exclude가 기본 제외 목록을 **대체**하기 때문이다. 기존 3개 항목(`README.txt`, `docs/`, `oled/ogpi_stats.py`)은 유지하고, `.gitignore`에 `node_modules`를 넣는다.

**빌드로도 안 되는 것**: `max-age` 연장, brotli, HTTP/3. 해시 파일명은 캐시 무효화를 정확하게 해줄 뿐 캐시 수명을 늘리지는 못한다. 이것들은 호스트를 옮겨야만 얻을 수 있다(§6 3-3, 조건부).

### 이 제약이 전략에 미치는 영향

- **서버 쪽 해법이 없으므로 "덜 보내고, 늦게 보내고, 덜 돌리는" 것이 전략의 전부다.** 다행히 측정상 병목의 대부분(숨겨진 히어로, 불필요한 JS, 원본 이미지, 쉬지 않는 애니메이션)이 이 범위 안에 있다.
- **변경 영향 범위는 홈페이지 한 장이다.** `assets/`, `data/`를 참조하는 HTML은 `index.html`뿐이다(grep). `playbook/`, `icqa/`, `khu-che/`, `proposal/`, `index_2021.html`은 자체 자산을 쓴다.
- **배포 직후 10분 동안은 새 HTML과 캐시된 옛 JS·CSS가 섞일 수 있다.** HTML과 JS·CSS를 함께 바꿔야 서로 맞물리는 변경(importmap 삭제, 스크립트 태그 삭제, CSS 병합·삭제, JSON 필드 변경)은 **새 파일명**으로 교체하거나 '추가 먼저, 삭제는 600초 뒤'의 2회 배포로 나눈다. 옛 파일은 최소 한 캐시 주기(600초) 이상 지난 뒤 지운다(D4).

## 4. 핵심 원칙

1. **첫 화면의 가시성을 JS에 묶지 않는다.** 히어로 문구·이미지·아이콘은 HTML과 CSS만으로 즉시 보여야 한다. 외부 CDN이 실패해도 첫 화면은 떠야 한다.
2. **모바일이 쓰지 않는 것은 모바일에 보내지 않는다.** 3D 라이브러리, 데스크톱용 고해상도 이미지, 화면 밖 차트 라이브러리는 조건부·지연 로드한다.
3. **화면 밖은 나중에 받는다.** 스크롤해야 보이는 이미지·차트·캐러셀·JSON은 가까워질 때 받는다.
4. **보이지 않는 것은 돌리지 않는다.** 화면 밖 캔버스, 투명한 애니메이션, 불투명 배경 위 blur, 백그라운드 탭의 타이머는 멈춘다.
5. **측정이 먼저다.** RUM을 먼저 붙여 기준선을 남기고, 변경마다 같은 조건에서 전후를 비교한다.
6. **짝이 있는 변경은 한 커밋에 넣는다.** 측정에서 확인한 짝은 다음과 같다: importmap 삭제와 정적 import 삭제, GSAP 태그 삭제와 IntersectionObserver 교체, 라이브러리 제거와 `theme.init` 호출 제거, `svg-inject` 클래스 제거(먼저)와 SVGInject 제거(나중). 이 넷은 하나만 적용하면 기능이 깨진다(측정). 히어로 `data-cue` 제거와 이미지 크기 지정도 짝으로 둔다. 이미지가 도착하는 타이밍에 따라 CLS가 악화될 수 있기 때문이다(조건 의존, §5-1 P1).

## 5. 개선 전략 — 계층별

이 절은 기술 영역별 상세이며 개발 담당자용이다. 실행 순서는 §6을, 경영 판단은 요약과 §6-1을 본다. 기호는 P=렌더링 경로, A=애니메이션, J=JavaScript, I=이미지, F=폰트, C=CSS, D=전달·캐시다. 주요 항목은 **문제 → 조치 → 기대 효과 → 위험·대응** 순서로 적었고, 작은 항목은 한 문단으로 적었다. 대괄호 안은 §6 로드맵의 단계와 번호다.

### 5-1. 렌더링 경로

**P1. 히어로를 JS 없이 바로 보이게 한다 (최우선)** `[0단계 0-1]`
- **문제**: §1-1 진단 1. 모바일에서 히어로 문구는 7.67초에 보이고, jQuery CDN이 실패하면 영구히 보이지 않는다.
- **조치**: `index.html:118`에서 `data-cues`, `data-group`, `data-delay`를, `:158`에서 `data-cue`, `data-delay`를 삭제한다. `:158`의 `cyber-float` 클래스는 **함께 삭제**해 현재처럼 정지된 모습을 유지한다(떠다니는 연출을 원하면 남기되 reduced-motion 가드를 추가, §6-1 #2). `:160` 히어로 이미지에는 `width="800" height="925"`를 추가한다. 등장 연출이 필요하면 JS 없이 CSS로 구현한다. 이때 opacity는 1에서 시작하고 transform만 움직이며, `.cyber-float` 요소가 아닌 안쪽 요소에 건다.
- **기대 효과**: 모바일 느린 4G 기준 히어로 문구 표시가 7.67초 → **3.60초**(단독 적용, 3회 중앙값, 검증 재측정 3.62초). 데스크톱 LCP는 6.5초 → 3.4~3.7초. 전송량 변화는 0이다. LCP 요소가 로고에서 히어로 문구로 바뀌어 지표가 체감과 일치하게 된다(모두 측정). 이 수정 후 scrollCue 대상은 0개가 되어 라이브러리와 CSS를 뺄 수 있다(J3, C1).
- **위험·대응**: 이미지에 크기가 없으면, 이미지가 첫 레이아웃 뒤에 도착하는 조건에서 세로 가운데 정렬된 히어로가 약 150px 튄다. 한 검증 실행(1440px, fast-4G, 스캔라인 끔)에서는 속성만 지웠을 때 CLS가 0.083 → 0.19~0.20으로 올랐지만, 재측정 9회(fast·slow 4G)에서는 0.0002~0.0009로 재현되지 않았다. 도착 타이밍에 따라 달라지므로 width/height 지정은 예방 조치로 같은 커밋에 넣는다(지정 후 0.0002~0.0009, 측정). 히어로 진입 애니메이션 제거는 §6-1 #1에서 정한다.

**P2. `<head>`의 동기 CDN 스크립트 3개 제거·지연** `[0단계 0-4]`
- **문제**: `index.html:37`(chart.js), `:40`(gsap), `:41`(ScrollTrigger), 합계 117.8KB br가 파서를 막고 `style.css`와 대역폭을 다툰다. GSAP은 `energy-management-animation.js:51-76`의 트리거 1건에만 쓰이고, ScrollTrigger는 로드 후에도 초당 약 58회의 rAF 루프와 250ms 타이머를 계속 돌린다(측정). Chart는 DOMContentLoaded 뒤에만 쓰인다.
- **조치**: `:40-41`을 삭제하고, 같은 커밋에서 `setupScrollTrigger()`를 `IntersectionObserver`(`rootMargin:'0px 0px -20% 0px'`)로 교체한다. 섹션을 벗어나면 멈추고, 탭 복귀 시 보이는 중이면 재개한다. `:37` chart.js에는 우선 `defer`를 붙이고, 이후 J1에서 지연 주입으로 바꾼다.
- **기대 효과**: defer만으로 FCP -0.32~0.55초(느린 4G, 측정). GSAP 제거와 IO 교체를 함께 하면 FCP 1.59 → 1.05초(CPU 4배, 네트워크 스로틀 없음, 측정). ScrollTrigger의 상시 rAF 루프(초당 약 58회)와 250ms 타이머가 사라진다. 파티클과 CSS 애니메이션은 A2·A3에서 별도로 처리한다. 전송 -47KB br.
- **위험·대응**: 태그만 지우면 폴백(`:52-55`)이 로드 직후부터 2.5초 타이머를 화면 밖에서도 영구히 돌린다. 교체는 필수다.

**P3. three.js를 데스크톱에서만 조건부 로드** `[0단계 0-5]`
- **문제**: `3d-effects.js:7`의 정적 `import`와 `index.html:28-34`의 importmap(minify되지 않은 빌드) 때문에 모바일도 전송 255KB(압축 해제 1.27MB)를 받아 평가한다. 모듈 스크립트라 DOMContentLoaded가 이를 기다린다. domInteractive 7.0초 vs DCL 9.8초로, **2.8초를 기다린다**(측정).
- **조치**: 정적 import를 지우고, CyberEffects 초기화 블록(`3d-effects.js:473-479`)에서 `innerWidth >= 992`이고 reduced-motion이 아닐 때만 `import('https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.module.min.js')`를 호출한다. HeroParticleEffect·Card3DTilt는 three를 쓰지 않으므로 게이트 밖에 둔다. importmap 삭제는 **같은 커밋**에 넣는다(importmap만 지우면 모듈 전체가 실패, 측정). 파일명을 바꿔(예: `3d-effects.v2.js`) 10분 캐시 혼합을 막는다. `async`를 쓴다면 `document.readyState` 분기를 넣는다.
- **기대 효과**: 모바일 DCL -2.8초, 프로젝트 표시 -2.4~2.5초, 모바일 전송 -250KB(측정). 데스크톱은 min 빌드로 -88KB br.
- **위험·대응**: 단독 적용 시 히어로 문구가 오히려 0.13~0.67초 늦어진다(DCL 작업이 앞당겨져서, 측정). **P1과 함께** 적용하면 상쇄된다. §6-1 #3에서 WebGL 배경을 제거하기로 정하면 이 작업은 importmap·정적 import·CyberEffects 삭제로 끝난다.

**P4. body 끝 스크립트 `defer`와 죽은 스크립트 삭제** `[0단계 0-6]`
- **문제**: `index.html:882-892`, `950`, `953`의 클래식 스크립트 10개(213KB)가 파서를 막는다. `:882` Bootstrap 번들(23.7KB br)은 `data-bs-` 속성이 0건이라 실행되는 기능이 없다. 오프캔버스 메뉴는 `theme.js:92-144`의 jQuery 코드다. `:890` `chatbot-ui.js`(6.3KB gz)는 초기화가 주석 처리되어 있다(`index.html:928-943`).
- **조치**: `:882`, `:890` 태그를 삭제하고, 나머지 외부 스크립트에 `defer`를 붙인다. 실행 순서는 jQuery → plugins → theme으로 유지된다. 인라인 초기화(`:895-947`)는 DOMContentLoaded 리스너라 그대로 호환된다.
- **기대 효과**: domInteractive 6.9초 → 3.7초, DCL -0.8초, 전송 -30KB(측정).
- **위험·대응**: **P3 없이 적용하면 히어로가 0.77초 늦어진다.** 일찍 요청된 three.js가 `plugins.js`와 대역폭을 다투기 때문이다(측정). 적용 순서는 P1 → P3 → P4로 고정한다. P1·P2·P3·P4·F3·I1·A1을 동시에 적용한 조합에서 오프캔버스, 스티키 헤더, 맨 위로 버튼, 캐러셀 37개, 차트 4개, 챗봇 데모, 에너지 애니메이션, 이메일 '확인하기' 버튼(`contact-reveal.js`, 이메일 보호 전략 Phase 2), GA 로드가 모두 정상이었고 페이지 오류는 0건이었다(측정).

### 5-2. 런타임 애니메이션

**A1. 스캔라인을 레이아웃 없는 애니메이션으로** `[0단계 0-2]`
- **문제**: `cyber-theme.css:423-437`의 `.cyber-scanline::before`가 `top`을 무한 애니메이션한다. 매 프레임 레이아웃이 일어나고 layout shift가 쌓여 모바일 CLS의 사실상 유일한 원인이 된다(CPU 4배 랩에서 모바일 0.13~0.15, 데스크톱 0.13~0.18, 측정). 데스크톱에서 조건에 따라 생기는 히어로 이미지 이동은 P1의 크기 지정으로 예방한다.
- **조치**: `top:0; will-change:transform`을 주고 `@keyframes scan{from{transform:translateY(0)} to{transform:translateY(100vh)}}`로 바꾼다. `@media (prefers-reduced-motion: reduce){.cyber-scanline{display:none}}`를 추가한다. 스캔라인 자체를 없앨지(`index.html:58`)는 §6-1 #5에서 정한다(권고: 유지).
- **기대 효과**: CLS → **0.000**(느린 4G와 스로틀 없음 모두), 프레임당 레이아웃 1.01 → 0.03회(측정). 모양은 동일하다.

**A2. 히어로 파티클 캔버스 최적화** `[1차 0단계 0-13, 2차 1단계 1-4]`
- **문제**: `3d-effects.js:276-414`는 파티클 100개를 모든 쌍으로 연결하고(모바일 프레임당 선 약 350~400개), 파티클마다 `shadowBlur`를 건다. 프레임 상한, 모바일 가드, 화면 밖 정지가 없어 `#Contact`에서도 초당 약 20회 돈다. 모바일 4배 조건에서 프레임당 약 7ms를 쓴다(측정).
- **조치**: **1차(0-13)** IntersectionObserver로 히어로가 보일 때만 rAF를 돌리고 벗어나면 `cancelAnimationFrame`한다. `innerWidth < 768`이면 파티클을 40개로 줄이고, 파티클마다 걸던 `shadowBlur`를 없앤다. **2차(1-4)** 발광은 미리 그려 둔 스프라이트(`document.createElement('canvas')`, `OffscreenCanvas`는 구형 Safari에서 2D를 지원하지 않음)로 되살리고, 30fps 상한을 둔다. 캔버스는 섹션 크기와 DPR 상한 1.5에 맞추고(`setTransform`, 마우스 좌표 보정), resize는 디바운스한다.
- **기대 효과**: 1차 조합(화면 밖 정지, 40개, `shadowBlur` 제거)에서 파티클 프레임 비용 -72%(측정). 화면 밖 정지만으로도 필터 탭 입력 지연이 142~214ms → 72~104ms로 줄었다(측정).
- **위험·대응**: `shadowBlur`를 없애면 발광이 약해지고 모바일 밀도가 줄어든다(§6-1 #4). 모바일에서 파티클을 **완전히 끄는** 것은 첫 화면 픽셀의 33%가 바뀌는 디자인 변경이다(측정). 권고는 유지하되 최적화하는 것이며, RUM에서 INP가 200ms를 넘으면 제거를 다시 검토한다(3-2).

**A3. 보이지 않는 무한 애니메이션 정지** `[0단계 0-12]`
- **문제**: 홀로그램 카드 `::after` 12개(500%×500% conic-gradient, `cyber-theme.css:121-156`)가 opacity 0 상태로 계속 회전한다. 터치 기기에서는 끝내 보이지 않는다. 전체 화면 그리드(`:52-71`)는 투명도 3%로 흐른다. 모바일 4배 조건에서 홀로그램만 끄면 프레임당 -2.9ms, 그리드만 끄면 -0.7ms였다(각 n=1, 측정).
- **조치**: `::after` 기본값을 `display:none`으로 두고 `@media (hover:hover)`의 `:hover`에서만 켜서 회전시킨다. **크기는 유지한다.** 150%로 줄이면 빛줄기가 카드 모서리에 닿지 않는다(측정). `display:none`에서 켜지면 opacity 전환(`:135`)이 동작하지 않으므로, fade-in이 필요하면 `@starting-style`을 점진적 향상으로 더한다. 그리드 `::before`는 애니메이션 또는 요소 자체를 삭제한다(숨겨도 변경 픽셀 ≤ 0.05%, 측정).
- **기대 효과**: 프레임당 약 -3~4ms(위 개별 측정값). 스캔라인(A1)과 셋을 함께 끄면 약 -8.4ms이며, 개별 값은 그대로 더해지지 않는다(측정). A1과 A3를 함께 적용하면 합성 레이어 105 → 88개(모바일 상단), 그리는 면적 66.8 → 27.6Mpx(-59%, 측정).

**A4. 효과 없는 backdrop-filter 제거** `[1단계 1-5]`
- **문제**: blur가 걸린 요소는 33개다. 그중 `.cyber-card` 17개는 배경이 불투명(`#1a1f3a`)해 blur가 보이지 않고, 홀로그램 12개도 변경 픽셀이 ≤ 0.015%다(측정).
- **조치**: `cyber-theme.css:84`의 `backdrop-filter`를 삭제하고 `isolation:isolate`를 추가한다. 오프캔버스(`:763`, 불투명도 0.98)도 삭제한다. navbar(`:688`)는 blur가 보이는 구간이 있으므로 §6-1 #7에서 정한다(권고: 유지. 모바일에서 끌 경우 `background`에 `!important` 필요).
- **기대 효과**: blur 합성 레이어 17~26개 → 0(측정). 메인 스레드 효과는 headless 측정에서 관측되지 않았다. GPU 비용 감소(추정).

**A5. 타이머·스크롤 핸들러 정리** `[1단계 1-6]` 멈추지 않는 반복 작업은 차트 5초(`data-visualization.js:594-605`), Owl 자동 갱신 500ms(기본값), 캐러셀 autoplay, 에너지 하이라이트 2.5초(`energy-management-animation.js:96-105`)다. 각각 IntersectionObserver와 `visibilitychange`로 정지·재개하고 Owl은 `autoRefresh:false`로 한다. 맨 위로 버튼의 스크롤 핸들러 2개(`theme.js:560-592`, 매번 문서 높이 계산)는 하나로 합치고 rAF 스로틀과 높이 캐시를 적용한다. 가만히 있을 때 타이머 발화는 초당 6.2회에서 약 0회가 된다(측정 기준 추정).

**A6. prefers-reduced-motion 지원** `[1단계 1-6]` 현재 사이트 코드에는 이 처리가 한 건도 없다(grep). 감속 모드 사용자에게도 애니메이션 14개와 캔버스 루프가 그대로 돈다(측정). `cyber-theme.css` 끝에 감속 블록을 넣고(스캔라인·파티클·3D 배경 숨김, 홀로그램 `::after` `display:none`), JS 쪽에 가드를 넣는다(3D·파티클 초기화, 에너지 순환, 챗봇 타이핑, Chart 애니메이션, Owl autoplay). 전역 감속 규칙은 홀로그램 `::after`를 중심에서 벗어나게 하므로 A3(0-12) 이후에 넣는다. CSS로 3D 배경을 숨길 때는 JS 가드가 필수다. 크기 0으로 WebGL이 초기화되면 비율이 NaN이 된다.

### 5-3. JavaScript

**J1. 차트를 보일 때 만든다** `[1단계 1-2]`
- **문제**: 화면 밖 캔버스 4개(`index.html:412`, `#LiveDemo` 426~515행)를 DCL 핸들러(`index.html:897-946`, 차트 생성 907-926)에서 즉시 생성한다. 384~593ms(CPU 4배) 롱태스크가 생기고, 5초 갱신 타이머(`data-visualization.js:594-605`)는 화면 밖이나 백그라운드 탭에서도 영구히 돈다.
- **조치**: `DataVisualization` 인스턴스는 DCL에 만들어 `window.dataVizInstance`를 유지한다(`index.html:510` 버튼이 참조). 캔버스가 뷰포트 600px 이내로 오면 chart.js를 동적으로 주입한다(`chart.umd.js` + `integrity` + `crossOrigin`). onload 뒤에 기본값 설정과 차트 생성을 한다. `startAutoUpdate`는 IntersectionObserver와 `visibilitychange`로 멈추고 재개한다.
- **기대 효과**: 초기 전송 -70.7KB br. 관측 창 전체 TBT -556ms, FCP 1.59초 → 1.21초(CPU 4배, 측정).

### 5-5. 폰트

**F1. Manrope `@import` 제거와 자체 호스팅** `[0단계 0-9]`
- **문제**: `style.css:8`의 Google Fonts `@import`는 731KB CSS를 다 받은 뒤 `fonts.googleapis.com`, `fonts.gstatic.com`으로 가는 직렬 체인을 만든다. 이 CSS는 렌더를 차단한다(해당 요청만 2초 늦추면 FCP가 0.79초 → 2.74초, 측정). `font-display`가 없어서 Manrope를 기다리는 동안 **한글을 포함한 글자 전체가 그려지지 않는다**(최대 3초, 프레임 캡처로 확인, 측정). Manrope는 라틴 문자('AI', 'IoT', '200+')에만 쓰인다. P1을 적용하면 히어로 문구가 LCP가 되므로, 그 표시 시점이 Manrope 도착에 묶인다. P2·P3 이후 첫 화면을 막는 서드파티 체인은 이것 하나만 남는다.
- **조치**: 기본안은 gstatic의 Manrope latin 가변 woff2 한 파일(약 24.6~24.8KB, 받는 시점의 버전을 고정해 커밋)을 `assets/fonts/manrope/`에 두고 `OFL.txt`를 함께 두는 것이다. CSS에 **weight 400·500·700 face 3개**(같은 URL, `font-display:swap`, latin unicode-range)를 선언하고, `<head>`에 `<link rel="preload" as="font" type="font/woff2" crossorigin>`을 넣는다. 배포는 둘로 나눈다(D4). 1차 배포에서 face와 preload를 추가하고(F3와 같은 새 파일명 CSS에 넣음), 600초 이상 뒤 2차 배포에서 `style.css:8`을 삭제한다. 자체 호스팅이 하루라도 늦어지면 그 사이 임시 조치로 `style.css:8`을 `@import url("https://fonts.googleapis.com/css2?family=Manrope:wght@400;500;700&display=swap");`로 바꾼다(FOIT만 즉시 제거되고 체인은 남는다). 대안 A는 시스템 폰트 스택이다(0B). `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", sans-serif`를 `cyber-theme.css:36`, `:root`의 `--bs-font-sans-serif` 재정의, `data-visualization.js:44` 세 곳에 적용한다(§6-1 #6에서 전환으로 정한 경우만, 1-12).
- **기대 효과**: 서드파티 origin 2개와 렌더 차단 체인 1단계가 사라지고 FOIT가 없어진다. Manrope woff2를 6초 늦춘 실험에서 히어로 소개문 LCP는 FOIT(현재) 2,256ms, swap 1,432ms였다(측정, 폰트가 느리게 올 때의 차이). FCP는 로컬 -0.1~0.26초(측정, 연결 비용 미반영), 실제 모바일 -0.3~0.9초(추정).
- **위험·대응**: `font-weight:200 800` 범위 face 하나로 선언하면, 지금 700으로 그려지는 굵기 600 텍스트 241개 노드가 실제 600으로 얇아진다(측정 폭 -1.9%). 그래서 face 3개로 선언하며, 이 기본안은 현재 모습을 그대로 유지하므로 디자인 승인이 필요 없다. preload와 `@font-face`의 URL이 다르거나 `crossorigin`이 빠지면 두 번 받는다. 대안 A는 라틴 글자 모양이 바뀐다(§6-1 #6). 이 항목은 **C2(CSS 번들)보다 먼저** 해야 한다. 번들 중간에 남은 `@import`는 무시되어 Manrope가 조용히 사라지고, computed style 비교로도 잡히지 않는다(측정).

### 5-7. 전달·캐시

**D1. www 없는 주소의 TLS 오류 해결** `[0단계 0-14, 저장소 밖, 담당: Vultr 서버·DNS 관리자]` `tabspace.kr`(A 레코드 158.247.214.232, Vultr)은 HTTPS가 4/4 실패하고, HTTP로 들어와야 `https://www.tabspace.kr/`로 301된다(측정). Vultr 서버(openresty)에 Let's Encrypt 인증서를 발급하고 443에서 `return 301 https://www.tabspace.kr$request_uri;`를 설정한다. 이 방식은 호스트 이전과 무관하게 유지되므로 apex를 GitHub IP로 바꾸는 방식보다 우선한다. 인증서 자동 갱신 cron과 만료 알림을 함께 설정한다. 명함·QR·네이버 서치어드바이저·블로그 링크는 `https://www.tabspace.kr/`로 통일한다.

**D2. DNS TTL 상향** `[0단계 0-14, 저장소 밖]` `www` CNAME TTL이 300초다. 한국 ISP에서 권한 서버 조회에 38~135ms, 이어지는 `github.io` 조회에 35~175ms가 걸렸다(측정). 방문이 드물어 리졸버 캐시가 비어 있으면 첫 방문에 0.1~0.3초가 더해질 수 있다(추정). 3600초 이상으로 올린다. 비용은 0이고 위험은 낮다(호스트 이전 계획이 생기면 그 전에 다시 낮춘다).

**D3. 초기 경로의 서드파티 연결 없애기, preconnect는 마지막에** `[1단계 1-11]` P2·P3·P4·J1을 적용하고 나면 초기 경로의 jsDelivr 요청은 없어지고 jQuery(cdnjs) 하나만 남는다. 이때 jQuery를 `assets/vendor/jquery-3.7.1.min.js`로 자체 호스팅한다. 파일은 gzip 30,288B이고 바이트가 같아 기존 `integrity`를 그대로 쓸 수 있다(측정). 이미 열린 HTTP/2 연결을 쓰므로 초기 경로의 서드파티 연결이 0이 된다. 재방문 시 600초가 지나면 304 재검증(약 0.4KB)이 생기지만, 방문량이 적은 사이트에서는 첫 방문 이득이 크다(추정). 초기 경로에 다른 jsDelivr 요청이 남아 있을 때만 jQuery를 jsDelivr로 합친다. 어느 경우든 jQuery는 `plugins.js`·`theme.js`·`data-loader.js`보다 앞 순서를 유지하고, P4 적용 후에는 이들과 같은 `defer` 그룹에 둔다(jQuery만 defer/async이고 `plugins.js`가 동기인 조합, jQuery의 `async`는 금지). 한국 모바일에서 새 origin마다 DNS(35~175ms, 측정)와 연결 수립이 DCL 경로에 더해지므로 origin을 없애는 편이 preconnect보다 낫다. preconnect는 이 정리 뒤에도 **초기 경로에 실제로 남는 origin에만** 최대 2~3개 둔다. `googletagmanager`에는 두지 않는다.

**D4. 캐시 혼합 방지 규칙** `[전 단계]` 엣지 캐시가 쿼리스트링을 무시하므로(측정) HTML과 계약이 바뀌는 JS·CSS는 **파일명**을 바꾼다(예: `3d-effects.v2.js`, `theme.home.js`, `plugins.home.js`, `cyber-theme.v2.css`). CSS를 합치거나 규칙을 옮기는 변경(F1, F3, C1)은 새 파일명으로 교체하거나, 2회 배포로 나눈다. 1차 배포에서는 추가만 한다(기존 링크·`@import` 유지, 중복 규칙은 같은 결과라 무해하다). 600초 이상 지난 뒤 2차 배포에서 링크·`@import`·옛 파일을 지운다. 이 규칙을 어기면 배포 후 최대 10분 동안 body 글자가 17px에서 16px로, h1이 50px에서 48px로 바뀌거나 Manrope가 빠진다(측정된 크기 차이). CSS만 바꾸고 HTML과의 계약이 그대로인 수정(A1, A3 등)은 같은 파일에서 해도 된다. 해시 파일명은 빌드 자동화(2단계) 후 자동으로 붙인다.

**D5. 빌드 방식 확정** `[1~2단계]` §2의 방식 A(로컬 실행 + 산출물 커밋)를 기본으로 한다. 1단계에서는 도구를 저장소 밖에서 1회 실행해 산출물만 커밋하고(C2, I4-a), 2단계에서 CI 동일성 검사와 해시 파일명 자동화를 더한다(2-1). 방식 B로 전환하려면 첫 배포에서 산출물 파일 목록이 현재와 같은지(`SECURITY.html` 렌더, `docs/` 제외) diff로 확인한다.

## 7. 효과 측정

**원칙**: 모든 비교는 **같은 조건에서 3회 이상의 중앙값**으로 한다. 랩 수치는 절대값보다 전후 차이로 읽는다. 최종 판정은 한국 실사용자 지표(RUM)로 한다.

**① 실사용자 지표(RUM), 0-0단계에서 가장 먼저**

```html
<!-- (1) <head>, 기존 gtag 정의 바로 뒤. 히어로 h1이 실제로 보인 시점을 잰다. P1 전후 비교가 끝나면 제거한다 -->
<script>(function p(){var h=document.querySelector('section h1');if(h&&parseFloat(getComputedStyle(h).opacity)>=0.99){window.__heroVisible=Math.round(performance.now());return;}if(performance.now()<15000)requestAnimationFrame(p);})();</script>

<!-- (2) index.html 끝. async라 DOMContentLoaded를 막지 않는다. web-vitals 버전은 적용 시점에 확인해 정확히 고정한다(작성일 기준 5.3.0) -->
<script type="module" async>
  import {onLCP, onINP, onCLS, onFCP, onTTFB} from 'https://cdn.jsdelivr.net/npm/web-vitals@5.3.0/dist/web-vitals.attribution.js';
  const ct = navigator.connection?.effectiveType || 'na';
  const tgt = a => (a?.target || a?.interactionTarget || a?.largestShiftTarget || '').slice(0, 100);
  const send = m => gtag('event', m.name, {
    value: Math.round(m.name === 'CLS' ? m.delta * 1000 : m.delta),
    metric_id: m.id, metric_value: m.value, metric_rating: m.rating,
    debug_target: tgt(m.attribution),
    lcp_render_delay: m.name === 'LCP' ? Math.round(m.attribution.elementRenderDelay) : undefined,
    effective_type: ct
  });
  [onLCP, onINP, onCLS, onFCP, onTTFB].forEach(f => f(send));
  const report = () => setTimeout(() => {
    const css = performance.getEntriesByType('resource')
      .find(e => e.name.startsWith(location.origin) && e.name.endsWith('.css') && e.transferSize > 0);
    const fcp = performance.getEntriesByName('first-contentful-paint')[0]?.startTime ?? 0;
    gtag('event', 'hero_visible', {
      // P1 이후에는 h1이 처음부터 불투명하므로, 실제로 그려진 시점은 FCP보다 이를 수 없다
      value: window.__heroVisible == null ? -1 : Math.round(Math.max(window.__heroVisible, fcp)),
      effective_type: ct,
      layout_overflow: document.documentElement.scrollWidth > innerWidth ? 1 : 0,
      css_wait: css ? Math.round(css.responseStart - css.requestStart) : -1
    });
  }, 3000);
  document.readyState === 'complete' ? report() : addEventListener('load', report);
</script>
```

- **0단계 판정은 LCP가 아니라 `hero_visible`로 한다.** 지금 브라우저 LCP API는 히어로가 투명해 로고를 LCP로 보고한다(3회 중 2~3회, 측정). 그래서 필드 LCP 기준선은 좋게 나오지만 실제 히어로 문구는 7.7초에야 보인다. P1 이후에는 LCP 요소가 로고에서 히어로 문구로 바뀌므로 필드 LCP는 거의 줄지 않거나 오히려 늘어 보일 수 있다(랩 LCP 중앙값 변화는 -0.3~0.5초뿐, 측정). **LCP 요소가 로고에서 히어로 문구로 바뀌는 것 자체가 P1의 성공 신호다.**
- `debug_target`, `lcp_render_delay`, `effective_type`, `layout_overflow`, `css_wait`은 GA4 맞춤 측정기준·측정항목으로 등록한다. `debug_target`은 CSS 선택자만 보내고 텍스트는 보내지 않으므로 이메일 주소가 전송되지 않는다. `css_wait`은 호스트 이전 판단(3-3)에 쓴다.
- GA4 탐색 보고서는 p75 같은 백분위 집계를 지원하지 않는다. **GA4 BigQuery 내보내기**(무료 샌드박스)를 0-0에서 켜고, SQL이나 Looker Studio로 한국·모바일 세그먼트의 p75를 본다. 내보내기는 켠 날부터만 쌓이고 과거 데이터를 소급하지 않는다. 2주 단위로 전후를 비교하되, **세그먼트별 표본이 100건 미만이면 p75로 판정하지 않는다.**

## 8. 정직한 한계 명시

- **한국 실사용자 수치는 아직 없다.** 모든 랩 측정은 미국을 경유하는 프록시 환경에서 했다. 한국 지연은 Globalping 단일 요청으로만 확인했고, 프로브 대부분이 고정망·데이터센터라 LTE/5G 무선 구간과 전체 페이지 로드는 한국에서 측정하지 못했다. PSI·CrUX 필드 데이터도 확보하지 못했다. **이 문서의 목표 달성 여부는 0-0단계의 RUM으로만 판정할 수 있다.**
- **랩 도구끼리 수치가 어긋난다.** 실사이트 Lighthouse는 프록시가 HTTP/1.1로 강등해 비관적으로 나왔다. 로컬 Lighthouse의 관측 FCP(약 2.25초)는 같은 뷰포트의 Playwright 측정(약 0.5초)과 맞지 않았고 원인을 분리하지 못했다. 일부 이미지 실험은 CDN 응답이 속도 제한을 받지 않았다. Lighthouse bootup-time이 ScrollTrigger에 2.3초를 돌리는 것도 같은 태스크의 레이아웃이 잘못 귀속된 것이다(실제 평가 약 30ms). 그래서 GSAP 제거 효과의 근거로 쓰지 않았다. 본문 수치는 되도록 **같은 조건의 전후 차이**로 인용했다. 아래 로컬 서버 측정 3건은 외부 CDN 8건이 실패한 불완전한 조건이라 판단 근거로 쓰지 않았다.

  | 대상·조건 | 실행 수 | 점수 | FCP | LCP | TBT | CLS | 전송량 / 요청 | 해석 |
  |---|---|---|---|---|---|---|---|---|
  | 로컬 서버(압축 없음, CDN 8건 실패) | 3회 | 57 | 7.74s | 15.77s | 10ms | 0.035 | 2,969,603B / 47 | jQuery 로드 실패로 JS 비용은 과소, 텍스트 바이트는 과대 |
  | 로컬 gzip 미러(CDN 8건 실패) | 3회 | 68 | 3.39s | 6.32s | 8ms | 0.037 | 1,389,312B / 45 | 자체 도메인 파일만 실사이트와 비슷함 |
  | 로컬 gzip 미러, 데스크톱 | 3회 | 98 | 0.76s | 1.04s | 0ms | 0.029 | 808,682B / 45 | 서드파티 620KB가 빠져 낙관적 |

- **모바일 기준선 일부는 넓어진 레이아웃에서 측정되었다.** 히어로 이미지 가시성, 레이어 면적, 첫 화면 높이 같은 모바일 수치 일부는 점 넘침 때문에 646px로 넓어진 레이아웃에서 측정되었다. 0-10 적용 후 모바일 기준선을 다시 잰다.
- **개별 효과의 크기는 조합에 따라 다르다.** 여러 JS 격리 실험의 TBT 차이는 2회 표본의 노이즈(±300ms) 안에 있었고, 일부는 오히려 나빠졌다. 확실히 재현된 것은 히어로 표시, FCP, 바이트 절감, 그리고 조합 효과다. 개별 수치를 더해 전체 효과로 쓰면 안 된다. 0단계 합계로 인용한 조합도 문서가 정의한 0단계 구성과 다르다(§6-2 '측정된 조합').
- **headless 환경에는 GPU가 없다.** 프레임 비용, blur 비용, WebGL 초기화 시간은 비관적으로 측정되었다. CPU 4배 감속은 중저가 안드로이드를 흉내 낸 것이며, 실제 기기 편차는 크다. 120Hz 화면에서는 상한 없는 파티클 루프가 두 배로 호출된다(추정). CLS도 프레임 간격에 비례해 조건마다 달라진다(CPU 4배 0.13~0.19, 스로틀 없음 0.04~0.11).
- **추정은 추정이다.** 실사이트 첫 화면 2.0MB, 전달 계층 기여 0.3~0.8초, 새 origin당 비용, DNS 비용, "방문 대부분이 식은 엣지를 만난다"는 판단은 모두 계산이나 가정에 기반한다. 방문량 데이터가 없다.
- **검증하지 못한 환경이 있다.** Safari(WebKit), 삼성 One UI의 시스템 폰트 매칭, 실제 앱 내 브라우저에서 www 없는 주소가 어떻게 보이는지는 확인하지 못했다. §7 ⑥의 실기기 확인으로 보완한다.
- **사이버 테마 연출은 경영 결정이지만 권고안은 분명하다.** 이 문서는 보이는 모양을 유지하면서 비용만 없애는 조치(transform 전환, 보이지 않는 blur·애니메이션 정지, 화면 밖 정지)를 먼저 배치했다. 모양이 바뀌는 항목은 측정된 시각 영향과 권고안을 함께 §6-1에 정리했다. 권고와 다르게 정하면 해당 행의 속도 효과를 포기하는 것이다.

## 9. 권고

1. **착수 전에 §6-1의 결정 4건을 정한다.** 히어로 등장 연출, 그림 떠다니는 효과, 데스크톱 3D 배경, 모바일 파티클 수준이다. 네 건 모두 권고안(없앤다 / 정지 유지 / 제거 / 유지하되 최적화)이 있다. 이것을 정해야 0-1, 0-5, 0-13의 작업 범위가 확정된다.
2. **RUM(0-0)을 먼저 배포해 기준선을 모은 뒤 0-1(히어로 `data-cue` 제거와 이미지 크기 지정)을 적용한다.** 기준선은 7일 또는 한국 모바일 page_view 100건 중 먼저 도달하는 시점까지 모은다. 방문량이 이보다 적어 기다릴 수 없으면 기준선은 §1의 랩 수치로 대신하고, RUM은 적용 후 절대값(목표 달성 여부) 추적에만 쓴다. 0-1은 속성 두 개를 지우고 크기 두 개를 넣는 30분짜리 작업이다. 모바일 첫 화면 핵심 문구가 7.7초에서 3.6초로 당겨지고, jQuery CDN 장애 때 첫 화면이 비는 문제도 함께 사라진다. 투입 대비 효과가 압도적으로 크다.
3. **모바일이 쓰지 않는 JS를 첫 화면 경로에서 빼는 작업은 한 묶음으로 진행한다.** 반드시 지킬 순서는 히어로 수정(0-1) → three.js 조건부 로드(0-5) → body 스크립트 defer와 Bootstrap·chatbot-ui 삭제(0-6) 하나다. 이 순서를 어기면 오히려 느려지는 조합이 측정되었다. GSAP 삭제와 chart.js defer(0-4)는 이 순서와 관계없이 언제 해도 된다.
4. **화면을 흔들고 대역폭을 뺏는 작은 결함을 같은 0단계에서 고친다.** 스캔라인을 transform으로 바꾸고(CPU 4배 랩 CLS 0.13~0.19 → 0), 모바일 캐러셀 점 넘침을 막고(페이지 축소 표시 해소), 캐러셀 사진 자리를 예약하고(사진 도착 시 이동 0.12 → 0), 맨 아래 일러스트에 lazy를 붙이고(-580KB), `svg-inject` 클래스를 지운다(아이콘 즉시 표시). Manrope도 자체 호스팅으로 바꿔 글자가 안 보이는 시간을 없앤다. 저장소 밖에서는 www 없는 주소의 인증서와 DNS TTL을 정리한다.
5. **1단계에서 "보이지 않는데 돌아가는 것"과 "쓰지 않는데 받는 것"을 정리한다.** 대상은 파티클 2차 최적화와 타이머 정지, 캐러셀 복제 제거와 지연 렌더, Unicons 서브셋, `plugins.js` 축소, 사진 같은 경로 축소, CSS 퍼지다. 0단계 뒤 재측정(0-G)에서 히어로가 FCP와 같아졌다면 CSS 퍼지(C2)부터 한다.
6. **호스트 이전은 지금 하지 않는다.** 현재 호스팅은 이미 서울에서 응답하고, 흔히 제안되는 Cloudflare 무료 프록시는 한국 사용자를 해외로 보낸다(측정). 1~2단계(CSS 퍼지, 사진 축소·파생본)를 마친 뒤, **RUM 데이터가 필요성을 보여줄 때만** CloudFront를 검토한다.
