# 이메일 주소 무단수집 방지 전략

작성일: 2026-08-17
대상: `www.tabspace.kr` (GitHub Pages 정적 사이트, 저장소 `tabspacekr/tabspacekr.github.io` — **공개 저장소**)
목적: 홈페이지의 이메일 주소가 자동 수집 프로그램에 의해 무단으로 수집되지 않도록 하고, 사람이 의도적으로 절차를 거쳐야만 확인할 수 있게 한다.

## 1. 현황 진단 — 노출 인벤토리

저장소 전체에서 `@tabspace.kr` 문자열이 **36곳**에서 평문으로 발견된다.

### 진단 요점

1. **JS 파일이 가장 큰 구멍이다.** 26건(전체의 72%)이 `.js` 안에 있다. 수집 프로그램은 HTML을 렌더링할 필요조차 없이 `.js` 파일을 그대로 내려받아 정규식 한 줄로 전부 긁어간다. 화면상 챗봇을 열지 않아도 노출된다.
2. **`README.txt`는 웹으로 직접 서빙된다.** 정적 호스팅이므로 저장소의 모든 파일이 URL로 공개된다. 인증·차단 장치가 없다.
3. **저장소가 공개(public)다.** 이것이 이 사이트만의 핵심 제약이다. GitHub 코드 검색과 저장소 클론으로 소스 전체를 볼 수 있으므로, **"소스에는 평문이 있고 화면에만 가리는" 방식의 난독화는 전부 무의미하다.** 방어는 반드시 *저장된 바이트 자체*에 평문이 없는 형태여야 한다.
4. **git 히스토리는 회수 불가능하다.** 이미 커밋된 주소는 히스토리·포크·GitHub 캐시·검색엔진 캐시에 남는다. 따라서 **현재 주소는 이미 유출된 것으로 간주**하고 전략을 세워야 한다. 이 사실이 아래 3계층(주소 교체)을 필수 항목으로 만든다.
5. **개인 식별성이 높은 주소가 노출되어 있다.** `ceo@`, `he086@`는 폐기하거나 교체하기 어려운 주소다. 스팸에 오염되어도 버릴 수 없다는 것이 가장 큰 손실이다.

## 2. 위협 모델 — 무엇을 막고, 무엇은 못 막는가

방어 설계 전에 상대를 구분한다. 이 구분 없이는 "완벽히 막았다"는 착각에 빠진다.

| 등급 | 공격자 | 수법 | 현재 | 목표 |
|---|---|---|---|---|
| **T1** | 대량 하베스터 (스팸 봇 대다수) | HTML·JS·TXT를 내려받아 `\S+@\S+` 정규식 매칭. JS 실행 안 함 | 전부 수집됨 | **완전 차단** |
| **T2** | 렌더링 하베스터 | 헤드리스 브라우저로 페이지를 열고 DOM 텍스트·`mailto:` 링크 수집. 클릭은 안 함 | 전부 수집됨 | **완전 차단** |
| **T3** | 표적형 봇 | 이 사이트 전용으로 스크립트를 분석하고 자동 클릭·연산까지 수행 | 수집됨 | **비경제화** (완전 차단 불가) |
| **T4** | 사람 | 직접 절차를 밟음 | 수집됨 | **차단하지 않음** (이것이 목적) |

**설계 목표를 명확히 한다: T1·T2를 100% 차단하고, T3의 비용을 "이 사이트 하나만을 위한 맞춤 개발"까지 끌어올린다.** 실제 스팸 피해의 99% 이상이 T1·T2에서 발생하므로 이것만으로 효과는 결정적이다. T3를 정적 사이트에서 완전히 막는 것은 원리적으로 불가능하며(클라이언트가 복호화할 수 있으면 봇도 할 수 있다), 이를 인정하고 4계층(피해 억제)으로 보완한다.

## 3. 핵심 원칙

1. **배포되는 어떤 파일에도 이메일 평문이 존재하지 않는다.** HTML·JS·CSS·TXT·주석 포함. 검증 가능한 불변식으로 만들어 CI로 강제한다.
2. **난독화가 아니라 암호화한다.** ROT13·base64·`String.fromCharCode`·`&#64;` 엔티티 치환은 소스가 공개된 이상 전부 무력하다. 복호화 키를 소스에 두지 않는다.
3. **사용자의 명시적 행동이 있어야만 DOM에 등장한다.** 클릭 이전에는 주소가 메모리에도 평문으로 존재하지 않는다.
4. **최선의 방어는 노출하지 않는 것이다.** 게이팅은 차선이다. 문의 폼·전화라는 대체 경로를 앞세워, 대다수 방문자가 이메일 주소를 알 필요조차 없게 만든다.
5. **유출을 전제로 설계한다.** 공개 주소는 언제든 폐기·교체 가능한 별칭이어야 한다. 오염되면 버리는 것이 최종 방어선이다.

## 4. 방어 아키텍처 — 4계층

```
┌─ 1계층 · 제거 ─────────────────────────────────────┐
│ 배포 산출물에서 이메일 평문 전면 삭제 (36건 → 0건)  │  → T1 차단
├─ 2계층 · 게이팅 ───────────────────────────────────┤
│ 클릭 + 연산 챌린지를 통과해야 복호화되는 암호문 배치 │  → T2 차단, T3 비용 상승
├─ 3계층 · 주소 교체 ────────────────────────────────┤
│ 개인 주소 → 폐기 가능한 공개 별칭으로 전환          │  → 기존 유출분 무력화
├─ 4계층 · 억제 및 정책 ─────────────────────────────┤
│ 대체 접점 우선 배치 · 수집거부 고지 · 회귀 방지 CI   │  → 잔여 위험 관리
└────────────────────────────────────────────────────┘
```

### 1계층 — 제거

- `index.html`, `index_2021.html`, `khu-che/*.html`의 `mailto:` 링크와 링크 텍스트 삭제 → 게이트 컴포넌트로 대체.
- 챗봇 JS 26건: 대사에서 이메일을 걷어내고 "문의하기 버튼을 눌러주세요" 형태로 전환하거나, 런타임에 게이트를 여는 액션 버튼으로 치환.
- `README.txt`의 CONTACT 항목 삭제(또는 웹 문의 안내로 대체). 필요하면 `README.txt`를 `_`로 시작하는 이름으로 옮겨 Jekyll이 배포에서 제외하도록 한다.
- `css/style.css`, `oled/ogpi_stats.py` 주석의 주소 제거.

### 2계층 — 게이팅 (핵심)

**동작 흐름**

```
[이메일 문의] 영역
   │  화면에는 주소 없음. DOM·소스 어디에도 평문 없음
   ▼
① 사용자가 "이메일 주소 확인" 버튼 클릭
   ▼
② 브라우저가 연산 챌린지 수행 (약 1~3초, 진행률 표시)
   SHA-256(seed‖nonce)의 상위 N비트가 0이 되는 nonce 탐색
   ▼
③ 찾은 nonce로 AES-GCM 키 유도 → data/contact.enc.json 복호화
   ▼
④ 주소 표시 + [복사] 버튼. 60초 후 자동으로 다시 숨김
   (mailto: 링크는 만들지 않는다)
```

**왜 이 구조인가**

- 암호문은 저장소에 커밋되지만, 복호화 키는 *어디에도 저장되지 않고* 실행 시점의 연산으로만 만들어진다. 공개 저장소를 통째로 받아도 주소를 얻을 수 없다 → T1 원천 차단.
- 클릭 없이는 연산이 시작되지 않으므로 DOM만 훑는 헤드리스 수집기는 아무것도 얻지 못한다 → T2 차단.
- T3에 대해서는 CPU 비용이 아니라 **개발 비용**이 방어선이다. 이 사이트 고유의 챌린지 형식을 해석하고 구현해야만 뚫린다. 대량 수집업자에게 사이트 하나를 위한 맞춤 개발은 채산이 맞지 않는다. (난이도를 CPU로 올리는 방식은 사람의 대기시간도 같이 늘어나므로 2^20~2^22비트 수준에서 멈추는 것이 옳다. 이 값을 "봇을 CPU로 막는 장치"로 과신하지 않는다.)

**설계 파라미터**

| 항목 | 값 | 근거 |
|---|---|---|
| 난이도 | 상위 20비트 (약 100만 해시) | 최신 브라우저에서 1~3초. 체감 한계선 |
| 연산 위치 | Web Worker | 메인 스레드 차단 방지, 진행률 표시 |
| 암호 | AES-GCM 256 (WebCrypto) | 표준·내장, 별도 라이브러리 불필요 |
| 키 유도 | PBKDF2-SHA256 (salt 16B) | 챌린지 해답 → 키 |
| 표시 후 | 60초 뒤 자동 은닉, `mailto:` 미생성 | 스크린 스크래핑 창 최소화 |
| 실패/JS 비활성 | 전화·문의폼 안내로 폴백 | 접근성 필수 |

**배포 산출물 예시** (`data/contact.enc.json` — 이 파일에 평문은 없다)

```json
{
  "v": 1,
  "seed": "tabspace-contact-2026-08",
  "difficulty": 20,
  "salt": "…base64…",
  "iv": "…base64…",
  "ct": "…base64(AES-GCM ciphertext)…"
}
```

**암호문 생성 도구** (`tools/gen-contact-cipher.mjs`, Node 18+, 주소 변경 시에만 1회 실행)

```js
// 평문 주소는 이 스크립트의 인자로만 전달하고 저장소에 커밋하지 않는다.
// node tools/gen-contact-cipher.mjs '{"sales":"…","tech":"…"}' > data/contact.enc.json
```

빌드 파이프라인이 없는 순수 정적 저장소이므로, **생성은 수동 1회 · 결과만 커밋**하는 방식이 유지보수 부담이 가장 적다.

### 3계층 — 주소 교체 (가장 실효성이 큰 조치)

기술적 게이팅보다 이쪽의 효과가 크다. 이미 유출된 주소는 어떤 방어를 해도 되돌릴 수 없기 때문이다.

- 홈페이지 공개용으로 **폐기 가능한 별칭**을 신설한다. 예: `sales@`, `support@`, `tech@` (혹은 `contact@`).
- `ceo@`, `he086@` 등 개인·대표 주소는 **홈페이지에서 완전히 제거**하고, 별칭에서 내부로 포워딩한다.
- 별칭에 스팸이 임계치를 넘으면 **그 별칭만 폐기하고 새 별칭으로 교체**한다. 홈페이지는 암호문 파일 한 개만 갈아끼우면 되므로 교체 비용이 사실상 0이다. 이 "언제든 버릴 수 있다"는 성질이 전략 전체의 최종 방어선이다.
- 가능하면 유입 경로별로 태그를 분리한다(`sales+web@`, `sales+catalog@` 등). 어느 경로에서 유출되었는지 사후에 특정할 수 있다.

### 4계층 — 억제 및 정책

**(a) 대체 접점을 이메일보다 앞에 배치**
"번거로운 절차"가 진짜 고객에게 장벽이 되면 안 된다. 이메일 게이트 위에 마찰 없는 경로를 둔다.

- 전화 (이미 게시 중: 대표번호·사무실·영업직통)
- 웹 문의 폼 — 정적 사이트에서도 외부 서비스로 구현 가능 (구글 폼, 네이버 폼, Formspree, 채널톡·카카오톡 채널 등)
- 문의 폼이 있으면 **대다수 방문자는 이메일 주소를 알 필요가 없어진다.** 회신을 통해 자연스럽게 알게 되므로, 노출 필요성 자체가 줄어든다. 전략적으로는 이 항목이 게이팅보다 우선순위가 높다.

**(b) 수집 거부 의사의 명시적 게시**
「정보통신망 이용촉진 및 정보보호 등에 관한 법률」 제50조의2는 **수집 거부 의사가 명시된 홈페이지**에서 자동 수집 프로그램으로 전자우편주소를 수집하는 행위를 금지하며, 위반 시 형사처벌 대상이 된다(제74조, 1년 이하 징역 또는 1천만원 이하 벌금 — 적용 전 최신 법령 확인 권장).
→ **거부 의사를 명시해야 법적 보호가 성립한다.** 푸터와 문의 섹션에 고지 문구를 게시한다.

> 본 웹사이트에 게시된 이메일 주소가 전자우편 수집 프로그램이나 그 밖의 기술적 장치를 이용하여 무단으로 수집되는 것을 거부하며, 이를 위반 시 정보통신망법에 의해 형사처벌됨을 유념하시기 바랍니다.

**(c) robots.txt 강화**
현재 `User-agent: * / Allow: /` 로 전면 허용이다. 하베스터가 robots.txt를 지킬 의무는 없지만, (b)의 "거부 의사 명시"를 뒷받침하는 근거로 기능한다. 알려진 수집·AI 크롤러에 대한 `Disallow`와 수집 거부 주석을 추가한다. 검색엔진(구글·네이버·다음) 색인은 유지해야 하므로 전면 차단은 하지 않는다.

**(d) 회귀 방지 — 이것이 없으면 전략은 반년 안에 무너진다**
새 페이지를 추가하면서 다시 `mailto:`를 넣는 것이 가장 흔한 실패 경로다. 자동 검사로 불변식을 강제한다.

```bash
# 배포 대상에 이메일 평문이 있으면 실패
git grep -InE '[A-Za-z0-9._%+-]+@tabspace\.kr' -- \
    ':!docs/' ':!tools/' && { echo "이메일 평문 발견"; exit 1; }
```

GitHub Actions 워크플로 또는 pre-commit 훅으로 연결한다.

**(e) 접근성 폴백**
게이트는 JS에 의존하므로, JS 비활성·스크린리더·구형 브라우저 사용자를 위해 `<noscript>`에 전화번호와 문의 폼 링크를 반드시 제공한다. 게이트 버튼에는 `aria-live` 영역으로 진행 상태를 안내한다.

> 선택 항목 주석: GitHub Pages를 유지한 채 Cloudflare Worker(무료 티어)에 검증 엔드포인트를 두면, Turnstile 통과자에게만 복호화 키를 내려주는 진짜 서버 검증이 가능하다. 정적 사이트의 원리적 한계(T3)를 넘는 유일한 방법이지만, 운영해야 할 구성요소가 하나 늘어난다. 스팸 피해가 Phase 0~3 이후에도 지속될 때 검토한다.

## 6. 효과 측정

- **노출 건수**: `git grep -cE '@tabspace\.kr'` 배포 대상 기준 0건 유지 (CI가 상시 검증)
- **원문 확인**: `curl -s https://www.tabspace.kr/{index.html,assets/js/chatbot-ui.js,README.txt} | grep -E '@tabspace\.kr'` → 무결과
- **렌더링 확인**: 헤드리스 브라우저로 페이지 로드 후 DOM 덤프에 주소 없음
- **실사용 확인**: 게이트 클릭 → 3초 이내 주소 노출, 복사 동작, 60초 후 은닉
- **운영 지표**: 별칭별 월간 스팸 수신량 추이 (증가 시 해당 별칭 폐기·교체)

## 7. 정직한 한계 명시

- 클라이언트가 복호화할 수 있는 이상, **충분히 동기가 강한 표적형 수집자는 반드시 뚫는다.** 이 전략은 그것을 막지 못하며, 막을 수 있다고 가정해서도 안 된다.
- **이미 커밋된 주소는 회수할 수 없다.** git 히스토리·포크·검색엔진 캐시·기존 유출 DB에 남는다. 3계층(주소 교체)이 유일한 근본 대책이다.
- 게이팅은 정당한 고객에게도 마찰을 준다. 반드시 마찰 없는 대체 경로(전화·문의 폼)와 함께 배치해야 하며, 그렇지 않으면 스팸을 줄이는 대신 문의를 잃는다.

## 8. 권고

Phase 0을 즉시 착수하고, Phase 1(별칭 교체)을 그 다음 우선순위로 둔다. 이 둘이 전체 효과의 대부분을 차지한다. Phase 2의 게이트는 "이메일 주소를 굳이 홈페이지에 계속 게시하겠다"는 결정이 유지될 때 의미가 있으며, Phase 3의 문의 폼이 자리를 잡으면 이메일 주소 게시 자체를 없애는 선택지도 진지하게 검토할 만하다.
