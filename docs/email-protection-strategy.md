# 이메일 주소 무단수집 방지 전략 (GitHub Pages 정적 호스팅 전제)

작성일: 2026-08-17
대상: `www.tabspace.kr` — **GitHub Pages 정적 호스팅**, 저장소 `tabspacekr/tabspacekr.github.io` (**공개 저장소**)
목적: 홈페이지의 이메일 주소가 자동 수집 프로그램에 의해 무단으로 수집되지 않도록 하고, 사람이 의도적으로 절차를 거쳐야만 확인할 수 있게 한다.
제약: **서버 사이드 코드를 실행할 수 없다.** 모든 대책은 정적 파일과 브라우저 실행 범위 안에서 완결되어야 한다.

## 1. 현황 진단 — 노출 인벤토리

저장소 전체에서 `@tabspace.kr` 문자열이 **36곳**에서 평문으로 발견된다. 전부 정적 파일이므로 전부 URL로 직접 열람된다.

| 파일 | 건수 | 노출 형태 | 위험도 |
|---|---|---|---|
| `assets/js/chatbot-demo-animation.js` | 14 | 챗봇 데모 대사에 `he086@tabspace.kr` 평문 | **최상** |
| `assets/js/chatbot-ui.js` | 12 | 자동응답 사전에 `he086@`, `ceo@` 평문 | **최상** |
| `index.html` (783–785행) | 3 | `<a href="mailto:...">` + 링크 텍스트 | **최상** |
| `index_2021.html` | 3 | `sales@tabspace.kr` 평문 (구버전 페이지) | 상 |
| `khu-che/20260318_khu-cae.html` | 1 | `mailto:ceo@tabspace.kr` | 상 |
| `README.txt` | 1 | `ceo@tabspace.kr` — **`https://www.tabspace.kr/README.txt`로 그대로 열람됨** | **최상** |
| `css/style.css` | 1 | 주석 내 `ceo@tabspace.kr` | 중 |
| `oled/ogpi_stats.py` | 1 | 주석 내 `ceo@tabspace.kr` | 중 |

### 진단 요점

1. **JS 파일이 가장 큰 구멍이다.** 26건(전체의 72%)이 `.js` 안에 있다. 수집 프로그램은 HTML을 렌더링할 필요조차 없이 `.js` 파일을 그대로 내려받아 정규식 한 줄로 전부 긁어간다. 화면상 챗봇을 열지 않아도 노출된다.
2. **정적 호스팅이므로 저장소의 모든 파일이 URL이 된다.** `README.txt`, `css/style.css`, `oled/ogpi_stats.py`의 주석까지 전부 공개 열람된다. 접근 제어라는 개념 자체가 없다.
3. **저장소가 공개(public)다.** 이것이 이 사이트만의 핵심 제약이다. GitHub 코드 검색과 저장소 클론으로 소스 전체를 볼 수 있으므로, **"소스에는 평문이 있고 화면에만 가리는" 방식의 난독화는 전부 무의미하다.** 방어는 반드시 *저장된 바이트 자체*에 평문이 없는 형태여야 한다.
4. **git 히스토리는 회수 불가능하다.** 이미 커밋된 주소는 히스토리·포크·GitHub 캐시·검색엔진 캐시에 남는다. 따라서 **현재 주소는 이미 유출된 것으로 간주**하고 전략을 세워야 한다. 이 사실이 아래 3계층(주소 교체)을 필수 항목으로 만든다.
5. **개인 식별성이 높은 주소가 노출되어 있다.** `ceo@`, `he086@`는 폐기하거나 교체하기 어려운 주소다. 스팸에 오염되어도 버릴 수 없다는 것이 가장 큰 손실이다.

## 2. GitHub Pages 제약 조건 — 쓸 수 있는 수단과 없는 수단

일반적인 이메일 보호 기법의 상당수는 서버를 전제한다. 이 사이트에서는 **처음부터 선택지에서 제외**해야 한다. 아래를 확정하고 나면 남는 설계 공간은 좁고 명확하다.

### 사용할 수 없는 수단 (서버 필요)

| 기법 | 왜 불가능한가 |
|---|---|
| CAPTCHA / reCAPTCHA / Turnstile **검증** | 위젯은 붙지만 토큰 검증에 서버 엔드포인트가 필수. 검증 없는 위젯은 장식일 뿐 봇을 전혀 막지 못한다 |
| 자체 문의 폼 처리 | `POST`를 받아 메일을 보낼 백엔드가 없다. GitHub Pages는 정적 GET만 응답한다 |
| 접근 빈도 제한(Rate limit) · IP 차단 · User-Agent 차단 | 요청 처리 계층에 개입할 수 없다 |
| `.htaccess`, 서버 설정, 응답 헤더 커스터마이즈 | Nginx/Apache 설정 불가. `X-Robots-Tag` 같은 헤더를 넣을 수 없다 |
| 서버 사이드 이메일 클로킹 (PHP 등) | 서버 언어 실행 불가 |
| 세션 · 로그인 · 접근 제어 | 상태를 서버에 둘 수 없다 |
| 접근 로그 분석 | 서버 로그에 접근할 수 없다. 게이트 통과 시도 횟수조차 알 수 없다 |

### 사용할 수 있는 수단 (정적 범위)

| 기법 | 비고 |
|---|---|
| **사용자 상호작용 게이트 ("확인하기" 버튼 클릭)** | **핵심 수단.** 순수 JS로 완결, 외부 의존성 없음 |
| 인코딩된 문자열 저장 (XOR + Base64 등) | 소스에서 정규식 매칭이 성립하지 않게 만든다 |
| `event.isTrusted` 검사 | 스크립트가 합성한 클릭 배제. 비용 0 |
| **Jekyll `exclude`** — 배포 산출물에서 파일 자체를 제외 | 정적 사이트에서 유일하게 "그 URL을 없애는" 수단. 현재 `_config.yml`은 `theme` 한 줄뿐이라 모든 파일이 그대로 배포된다 |
| `robots.txt` · `<meta name="robots">` | 응답 헤더를 못 쓰므로 메타 태그로 대체 |
| 페이지 내 수집거부 고지문 | 법적 보호 요건 (§4-b) |
| **GitHub Actions** 회귀 방지 검사 | 호스팅이 아니라 저장소 측 CI. 정적 사이트와 무관하게 사용 가능 |
| 외부 호스팅 문의 폼 링크·임베드 | 폼은 구글·네이버 쪽에서 처리되고, 우리 쪽은 링크나 `iframe` 한 줄이므로 정적 유지 |

### 이 제약이 전략에 미치는 영향

**서버 검증이라는 최종 수단이 없다는 것은, 아무리 정교하게 만들어도 표적형 봇(§3의 T3)을 원리적으로 막을 수 없다는 뜻이다.** 브라우저가 복호화할 수 있으면 봇도 같은 코드를 실행하면 된다. 따라서 이 사이트의 전략은 다음과 같이 무게중심이 이동한다.

- 기술적 게이팅은 **T1·T2 차단**까지를 목표로 하고, 그 이상을 기대하지 않는다.
- **복구 가능성**이 핵심 통제 수단이 된다. 즉 오염되면 버릴 수 있는 별칭 주소(3계층)가 정적 사이트에서 실질적인 최종 방어선이다.
- 근본적으로는 **이메일 주소를 사이트에 두지 않고 외부 문의 폼으로 대체**하는 것이 정적 환경에서 가장 확실한 해법이다.

## 3. 위협 모델 — 무엇을 막고, 무엇은 못 막는가

| 등급 | 공격자 | 수법 | 현재 | 정적 환경에서의 목표 |
|---|---|---|---|---|
| **T1** | 대량 하베스터 (스팸 봇 대다수) | HTML·JS·TXT를 내려받아 `\S+@\S+` 정규식 매칭. JS 실행 안 함 | 전부 수집됨 | **완전 차단 가능** |
| **T2** | 렌더링 하베스터 | 헤드리스 브라우저로 페이지를 열고 DOM 텍스트·`mailto:` 링크 수집. 클릭은 안 함 | 전부 수집됨 | **완전 차단 가능** |
| **T3** | 표적형 봇 | 이 사이트 전용으로 스크립트를 분석하고 자동 클릭·연산까지 수행 | 수집됨 | **차단 불가.** 비용 상승만 가능 |
| **T4** | 사람 | 직접 절차를 밟음 | 수집됨 | 차단하지 않음 (이것이 목적) |

**목표를 정직하게 확정한다: T1·T2를 100% 차단하고, T3는 포기하되 3계층으로 피해를 회수 가능하게 만든다.** 실제 스팸 피해의 99% 이상이 T1·T2에서 발생하므로 이것만으로 효과는 결정적이다. T3를 막으려면 서버 검증이 필요한데 이 환경에는 없다 — 있는 척하는 설계를 하지 않는 것이 중요하다.

## 4. 핵심 원칙

1. **배포되는 어떤 파일에도 이메일 평문이 존재하지 않는다.** HTML·JS·CSS·TXT·주석 포함. 검증 가능한 불변식으로 만들어 CI로 강제한다.
2. **화면에서 가리는 것이 아니라 소스 바이트에서 없앤다.** `display:none`, `&#64;` 엔티티 치환, 클릭 시 평문 문자열 대입 방식은 소스가 공개된 이상 전부 무력하다. 반대로 인코딩 강도 자체는 중요하지 않다 — 정규식 매칭만 성립하지 않으면 목적을 달성한다.
3. **사용자의 명시적 행동이 있어야만 DOM에 등장한다.** 클릭 이전에는 주소가 메모리에도 평문으로 존재하지 않는다.
4. **최선의 방어는 노출하지 않는 것이다.** 게이팅은 차선이다. 외부 문의 폼·전화라는 대체 경로를 앞세워, 대다수 방문자가 이메일 주소를 알 필요조차 없게 만든다.
5. **유출을 전제로 설계한다.** 서버 검증이 불가능한 환경에서는 "뚫렸을 때 갈아끼울 수 있는가"가 유일하게 신뢰할 수 있는 통제다.

## 5. 방어 아키텍처 — 4계층

```
┌─ 1계층 · 제거 ─────────────────────────────────────┐
│ 배포 산출물에서 이메일 평문 전면 삭제 (36건 → 0건)  │  → T1 차단
│ + Jekyll exclude로 불필요 파일은 URL 자체를 제거     │
├─ 2계층 · 게이팅 ───────────────────────────────────┤
│ "확인하기" 버튼 클릭 시에만 디코딩되어 화면에 등장   │  → T2 차단
├─ 3계층 · 주소 교체 ────────────────────────────────┤
│ 개인 주소 → 폐기 가능한 공개 별칭으로 전환          │  → 기존 유출·T3 피해 회수
├─ 4계층 · 억제 및 정책 ─────────────────────────────┤
│ 외부 문의 폼 우선 배치 · 수집거부 고지 · 회귀 방지 CI │  → 노출 필요성 자체 감소
└────────────────────────────────────────────────────┘
```

### 1계층 — 제거

- `index.html`, `index_2021.html`, `khu-che/*.html`의 `mailto:` 링크와 링크 텍스트 삭제 → 게이트 컴포넌트로 대체.
- 챗봇 JS 26건: 대사에서 이메일을 걷어내고 "문의하기 버튼을 눌러주세요" 형태로 전환하거나, 런타임에 게이트를 여는 액션 버튼으로 치환.
- `css/style.css`, `oled/ogpi_stats.py` 주석의 주소 제거.
- **`_config.yml`에 `exclude`를 추가해 웹에 노출될 필요가 없는 파일을 배포에서 제외한다.** 정적 사이트에서 "이 URL을 없앤다"를 실현하는 유일한 수단이다. 현재 설정은 `theme` 한 줄뿐이라 아무것도 제외되지 않고 있다.

```yaml
theme: jekyll-theme-slate

exclude:
  - README.txt          # 현재 https://www.tabspace.kr/README.txt 로 열람됨
  - SECURITY.md
  - docs/               # 본 전략 문서 — 저장소에는 두되 웹에는 배포하지 않음
  - oled/ogpi_stats.py
```

> 주의: 이 저장소는 front matter 없는 순수 HTML 파일들을 Jekyll이 그대로 통과시키는 구조다. `exclude`는 안전 모드(safe mode)의 기본 GitHub Pages 빌드에서도 동작하므로 추가 구성 없이 즉시 쓸 수 있다. 다만 배포 제외는 **앞으로의 노출을 막을 뿐, 이미 색인·캐시된 내용을 지우지는 못한다.**

### 2계층 — 게이팅 : "확인하기" 버튼

**동작 흐름** — 전 과정이 브라우저 안에서 완결된다. 서버 왕복도, 대기 시간도 없다.

```
[이메일 문의] 영역
   │  화면에는 주소 없음. DOM·소스 어디에도 평문 없음
   │  [ 이메일 주소 확인하기 ]  ← 버튼만 표시
   ▼
① 사용자가 버튼 클릭
   ▼
② event.isTrusted 확인 (스크립트가 만든 가짜 클릭 배제)
   ▼
③ 인코딩된 문자열을 즉시 디코딩
   ▼
④ 주소 표시 + [복사] 버튼 (+ mailto: 링크는 이 시점에 생성해도 무방)
```

**설계의 핵심은 "무엇으로 잠그느냐"가 아니라 다음 세 가지다.**

1. **소스 바이트에 평문이 없을 것.** 저장소가 공개이므로 이것이 전부다. `display:none`으로 감추거나 클릭 시 평문 문자열을 대입하는 방식은 소스를 긁으면 그대로 드러나므로 **아무 효과가 없다.**
2. **클릭 전에는 DOM에 없을 것.** 렌더링 수집기(T2)를 막는 조건이다.
3. **`mailto:`를 사전에 만들어두지 않을 것.** `mailto:` 링크는 수집기가 가장 먼저 찾는 표식이다.

**구현 예시**

```js
// 소스에는 인코딩된 문자열만 존재한다 — 정규식 수집기에는 아무것도 걸리지 않는다
const ENC = 'PxQ2R1c…';

btn.addEventListener('click', (e) => {
  if (!e.isTrusted) return;        // 스크립트가 합성한 클릭 차단
  out.textContent = decode(ENC);
  copyBtn.hidden = false;
});
```

`e.isTrusted`는 `element.click()`처럼 스크립트로 합성한 이벤트에서 `false`가 된다. `document.querySelectorAll('button').forEach(b => b.click())` 식으로 버튼을 전부 눌러보는 흔한 수집 스크립트를 한 줄로 걸러내며, 실제 사용자에게는 아무 영향이 없다. 헤드리스 브라우저의 실제 클릭까지 막지는 못하지만, 비용이 0이므로 넣지 않을 이유가 없다.

**인코딩 방식** — XOR + Base64 정도면 충분하다. 목적은 암호학적 비밀 유지가 아니라 **정규식 매칭을 성립하지 않게 만드는 것**이기 때문이다. 키를 소스에 두든 두지 않든 T3는 어차피 막을 수 없으므로(§3), 복잡도를 올려도 얻는 것이 없다. 주소 변경 시에는 인코딩된 문자열만 바꿔 커밋한다.

**설계 파라미터**

| 항목 | 값 | 근거 |
|---|---|---|
| 트리거 | 명시적 버튼 클릭 1회 | T2 차단에 필요한 최소 조건이자 충분 조건 |
| 클릭 검증 | `event.isTrusted` | 합성 클릭 배제. 비용 0 |
| 저장 형태 | XOR + Base64 문자열 (HTML 또는 JS 내) | 정규식 무력화가 목적. 별도 파일·빌드 불필요 |
| 표시 후 | 유지 + [복사] 버튼 | 자동 은닉은 봇에겐 무의미하고 사용자만 불편하게 한다 |
| JS 비활성 | 전화·외부 문의 폼 안내로 폴백 | 접근성 필수 |

> **연산 챌린지(PoW)를 넣지 않는 이유** — 초안에서는 SHA-256 기반 연산 챌린지로 복호화 키를 유도하는 방식을 검토했으나 채택하지 않았다. 클릭까지 수행하는 수집기는 연산도 그대로 수행하므로 **추가로 차단되는 구간이 없고**, 실제 사용자에게만 1~3초의 대기가 생긴다. 방어 이득 없이 UX와 구현 복잡도만 늘어나는 교환이다. (§6 채택하지 않은 선택지)

### 3계층 — 주소 교체 (정적 환경에서 가장 실효성이 큰 조치)

서버 검증이 불가능한 이상, **"뚫린 뒤에 회복할 수 있는가"가 전략의 실질적 성패를 가른다.** 이 계층이 그 답이다.

- 홈페이지 공개용으로 **폐기 가능한 별칭**을 신설한다. 예: `sales@`, `support@`, `tech@` (혹은 `contact@`).
- `ceo@`, `he086@` 등 개인·대표 주소는 **홈페이지에서 완전히 제거**하고, 별칭에서 내부로 포워딩한다.
- 별칭에 스팸이 임계치를 넘으면 **그 별칭만 폐기하고 새 별칭으로 교체**한다. 홈페이지는 인코딩된 문자열 한 줄만 갈아끼우고 커밋하면 되므로 교체 비용이 사실상 0이다.
- 가능하면 유입 경로별로 태그를 분리한다(`sales+web@`, `sales+catalog@` 등). 어느 경로에서 유출되었는지 사후에 특정할 수 있다. 정적 사이트에는 접근 로그가 없으므로, **이것이 유출 경로를 파악할 수 있는 거의 유일한 수단이다.**

### 4계층 — 억제 및 정책

**(a) 대체 접점을 이메일보다 앞에 배치**
"번거로운 절차"가 진짜 고객에게 장벽이 되면 안 된다. 이메일 게이트 위에 마찰 없는 경로를 둔다.

- 전화 (이미 게시 중: 대표번호·사무실·영업직통)
- **외부 호스팅 문의 폼** — 구글 폼, 네이버 폼, 채널톡·카카오톡 채널 등. 폼 처리는 해당 서비스에서 이뤄지고 우리 사이트에는 링크나 `iframe` 한 줄만 들어가므로 **정적 호스팅 제약에 걸리지 않는다.**
- 문의 폼이 있으면 **대다수 방문자는 이메일 주소를 알 필요가 없어진다.** 회신을 통해 자연스럽게 알게 되므로, 노출 필요성 자체가 줄어든다. 서버를 쓸 수 없는 환경에서는 이 항목이 게이팅보다 전략적 우선순위가 높다.

**(b) 수집 거부 의사의 명시적 게시**
「정보통신망 이용촉진 및 정보보호 등에 관한 법률」 제50조의2는 **수집 거부 의사가 명시된 홈페이지**에서 자동 수집 프로그램으로 전자우편주소를 수집하는 행위를 금지하며, 위반 시 형사처벌 대상이 된다(제74조, 1년 이하 징역 또는 1천만원 이하 벌금 — 적용 전 최신 법령 확인 권장).
→ **거부 의사를 명시해야 법적 보호가 성립한다.** 기술적 차단이 원리적 한계를 갖는 정적 환경에서, 이 조치는 비용이 거의 없으면서 유일하게 T3까지 겨냥할 수 있는 억제 수단이다. 푸터와 문의 섹션에 게시한다.

> 본 웹사이트에 게시된 이메일 주소가 전자우편 수집 프로그램이나 그 밖의 기술적 장치를 이용하여 무단으로 수집되는 것을 거부하며, 이를 위반 시 정보통신망법에 의해 형사처벌됨을 유념하시기 바랍니다.

**(c) robots.txt · 메타 태그**
현재 `User-agent: * / Allow: /` 로 전면 허용이다. 하베스터가 robots.txt를 지킬 의무는 없지만, (b)의 "거부 의사 명시"를 뒷받침하는 근거로 기능한다. 알려진 수집·AI 크롤러에 대한 `Disallow`와 수집 거부 주석을 추가한다.
응답 헤더(`X-Robots-Tag`)를 설정할 수 없으므로, 개별 페이지 단위 제어가 필요하면 `<meta name="robots" content="noindex">`를 사용한다. 검색엔진(구글·네이버·다음) 색인은 유지해야 하므로 전면 차단은 하지 않는다.

**(d) 회귀 방지 — 이것이 없으면 전략은 반년 안에 무너진다**
새 페이지를 추가하면서 다시 `mailto:`를 넣는 것이 가장 흔한 실패 경로다. **GitHub Actions는 호스팅이 아니라 저장소 측 CI이므로 정적 사이트 제약과 무관하게 사용할 수 있다.**

```bash
# 배포 대상에 이메일 평문이 있으면 실패
git grep -InE '[A-Za-z0-9._%+-]+@tabspace\.kr' -- \
    ':!docs/' && { echo "이메일 평문 발견"; exit 1; }
```

`.github/workflows/`에 검사 워크플로를 추가한다. 이 워크플로는 사이트를 빌드하거나 배포하지 않으므로 기존 GitHub Pages 배포 방식에 영향을 주지 않는다.

**(e) 접근성 폴백**
게이트는 JS에 의존하므로, JS 비활성·스크린리더·구형 브라우저 사용자를 위해 `<noscript>`에 전화번호와 문의 폼 링크를 반드시 제공한다. 게이트 버튼에는 `aria-live` 영역으로 진행 상태를 안내한다.

| 이미지로 이메일 주소 표시 | OCR로 뚫리고, 복사 불가·스크린리더 불가로 접근성이 크게 나빠진다. 얻는 것보다 잃는 것이 크다 |
| CSS `::before`/`direction: rtl` 트릭, HTML 엔티티 치환 | 공개 저장소에서는 소스에 평문이 그대로 남는다. **1계층 원칙 위반** |

## 7. 효과 측정

정적 호스팅에는 접근 로그가 없으므로, 서버 측 지표(차단 횟수, 봇 트래픽 비율)는 측정할 수 없다. **저장소·응답 본문 검사와 메일함 지표로 대체한다.**

- **노출 건수**: `git grep -cE '@tabspace\.kr'` 배포 대상 기준 0건 유지 (GitHub Actions가 상시 검증)
- **원문 확인**: `curl -s https://www.tabspace.kr/{index.html,assets/js/chatbot-ui.js} | grep -E '@tabspace\.kr'` → 무결과
- **배포 제외 확인**: `curl -o /dev/null -w '%{http_code}' https://www.tabspace.kr/README.txt` → `404`
- **렌더링 확인**: 헤드리스 브라우저로 페이지 로드 후 DOM 덤프에 주소 없음
- **실사용 확인**: "확인하기" 클릭 → 즉시 주소 노출, 복사 버튼 동작, JS 비활성 시 폴백 노출
- **운영 지표**: 별칭별 월간 스팸 수신량 추이. **정적 환경에서 사실상 유일한 실효성 지표이며, 증가 시 해당 별칭을 폐기·교체한다**

## 8. 정직한 한계 명시

- **서버 검증 수단이 없으므로 표적형 수집자(T3)는 막을 수 없다.** 브라우저가 복호화할 수 있으면 봇도 같은 코드를 실행할 수 있다. 이는 구현 품질의 문제가 아니라 정적 호스팅의 원리적 상한이다.
- **이미 커밋된 주소는 회수할 수 없다.** git 히스토리·포크·검색엔진 캐시·기존 유출 DB에 남는다. `exclude`로 배포에서 빼도 이미 색인된 내용은 지워지지 않는다. 3계층(주소 교체)이 유일한 근본 대책이다.
- **게이팅은 정당한 고객에게도 마찰을 준다.** 반드시 마찰 없는 대체 경로(전화·외부 문의 폼)와 함께 배치해야 하며, 그렇지 않으면 스팸을 줄이는 대신 문의를 잃는다.

## 9. 권고

Phase 0을 즉시 착수하고, Phase 1(별칭 교체)을 그 다음 우선순위로 둔다. 이 둘이 전체 효과의 대부분을 차지하며, 정적 환경에서는 특히 Phase 1의 **"오염되면 버린다"** 는 성질이 유일하게 신뢰할 수 있는 통제 수단이다.

Phase 2의 게이트는 "이메일 주소를 굳이 홈페이지에 계속 게시하겠다"는 결정이 유지될 때 의미가 있다. Phase 3의 외부 문의 폼이 자리를 잡으면, **서버를 쓸 수 없는 환경에서 가장 확실한 해법은 이메일 주소 게시를 아예 없애는 것**이라는 선택지를 진지하게 검토할 만하다.
